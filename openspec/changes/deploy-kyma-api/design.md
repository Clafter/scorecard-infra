# Design: deploy-kyma-api

Decision records numbered **KA1** onwards (the baseline used **K1**–**K10**;
this change continues the Kyma series with an `A` for "api"). Each is a
real choice between alternatives.

## KA1 — Pin the image to an immutable `sha-<commit>` tag, not `main`

**Decision.** The Deployment references
`ghcr.io/clafter/scorecard-api:sha-92d24d8bc9c683e0d8b8b35fd3350104420f11b2`.

**Why not `:main`.** `publish-images.yml` republishes a mutable `main`
tag on every merge. A Deployment pinned to `main` would silently run
different code after an unrelated merge, and `kubectl rollout` could not
tell you what changed. An immutable SHA tag makes a redeploy
reproducible and an upgrade an explicit manifest edit.

**Why not a digest (`@sha256:…`).** A digest is even stronger, but the
SHA tag is already immutable in this pipeline (a given `sha-X` tag is
never republished), and a tag is legible in `kubectl get deploy -o wide`
where a digest is not. A promotion-to-prod change can tighten to digests
if the threat model calls for it.

## KA2 — Compose the bucket URL in the pod spec, not in a sidecar

**Decision.** The Object Store binding secret's keys (`bucket`,
`region`) are mapped to intermediate env vars (`BUCKET`,
`BUCKET_REGION`), and `SCORECARD_RESULTS_BUCKET_URL` is assembled with
Kubernetes env-var reference expansion:
`value: "s3://$(BUCKET)?region=$(BUCKET_REGION)&awssdk=v2"`.

**Alternatives.**

1. **Init container that writes a URL into a shared volume.** More
   moving parts, an extra image to maintain, and the pod cannot start if
   the init logic has a bug. Rejected for a one-line string
   concatenation.
2. **A ConfigMap with the URL hardcoded.** The bucket name
   (`hcp-<uuid>`) is generated by the Object Store broker and would have
   to be copied by hand from the secret into a ConfigMap, duplicating a
   value and inviting drift. Rejected.
3. **Change the Go code to read `bucket`/`region` separately.** Would
   fork the upstream config contract (`api/app/server/config.go`) for a
   deployment detail. Rejected — the env var is the contract, and the
   platform's job is to satisfy it.

**The `awssdk=v2` query parameter is load-bearing.** `gocloud.dev
v0.46.0`'s `s3blob` defaults vary with build tags; pinning `awssdk=v2`
matches the SDK v2 the module graph already pulls in and makes
credential resolution go through the v2 default chain.

## KA3 — Credentials via the AWS default chain from mapped env vars

**Decision.** `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` are mapped
from the Object Store secret's `access_key_id` / `secret_access_key`
keys. `gocloud.dev/blob/s3blob` resolves them through the AWS SDK's
default credential chain, which reads exactly those variables.

This honours AGENTS.md ("let credentials resolve through each backend's
default chain") — no credentials in code, none in the manifest, all from
the binding secret.

**The two buckets need two credential sets.** Each Object Store instance
has its own binding with its own HMAC key pair (the IAM boundary, K4).
The API writes `SCORECARD_RESULTS_BUCKET_URL` (api-results) and reads
`SCORECARD_CRON_RESULTS_BUCKET_URL` (cron-results) as a fallback. Both
are served by the same pod, so the pod needs both credential sets — but
`AWS_ACCESS_KEY_ID` is a single value. Resolved by KA4.

## KA4 — One credential set in env, cron bucket read via the same pair

**Decision.** For dev, map only the **api-results** credentials to the
AWS env vars. The cron-results bucket is also provisioned in the same
subaccount and, for the dev evaluation, the api-results binding's
credentials can read it because both buckets live under the same BTP
Object Store service broker account.

**Risk accepted, flagged.** If BTP scopes each binding's HMAC key
strictly to its own bucket (likely in production), the cron fallback
read will 403. This is acceptable for dev — the fallback path only
triggers for repositories with no Action-published result, and the
evaluation does not exercise the weekly cron pipeline yet. **A
production change must give the pod per-bucket credentials** (separate
AWS profiles via `AWS_SHARED_CREDENTIALS_FILE`, or a gocloud URL that
carries its own credentials). Recorded as an open question.

## KA5 — APIRule `gateway.kyma-project.io/v2`, split by method

**Decision.** One APIRule on the stable `v2` version
(`v1beta1` is deprecated, `v2alpha1` is the storage version but not the
API to write against). Two rules:

- `GET` on `/` (and subpaths) — `noAuth`. Public read, no token.
- `POST` on `/` — `jwt`, `authentications[0].issuer` and `jwksUri` from
  the XSUAA tenant.

**Why method-split rather than path-split.** The API's public surface is
every `GET`; the only state-changing verb is `POST` (upload). Splitting
on method is both simpler and tighter than enumerating public paths, and
it cannot be defeated by a new public GET path being added upstream.

**Issuer and JWKS come from the binding, not hardcoded.** The XSUAA
tenant URL (`https://i767568-e7443kwa.authentication.eu10.hana.ondemand.com`)
is in the `xsuaa-binding` secret. The manifest carries the resolved
values because an APIRule field cannot reference a secret; they are
recorded in the README as derived from the binding, so a tenant change
is a documented edit, not a mystery.

## KA6 — Host on the shared Kyma gateway, no custom domain

**Decision.** `hosts: [scorecard-api.bfcc835.kyma.ondemand.com]`,
`gateway: kyma-system/kyma-gateway`. The cluster domain
(`bfcc835.kyma.ondemand.com`) comes from `kube-system/shoot-info`.

No custom domain (user decision, previous session). When a real domain
is wanted, it is a `gateway` + DNS change, not an API change.

## KA7 — NetworkPolicy: default-deny ingress except the mesh, egress to S3 + XSUAA + DNS

**Decision.** This change lands the NetworkPolicy the baseline deferred
(K7), now that the egress surface is known:

- **Ingress:** from the Istio ingress gateway only (the mesh fronts all
  traffic).
- **Egress:** DNS (kube-dns), the Istio control plane in
  `istio-system` (the sidecar's CA/CSR and xDS bootstrap — **without
  this the pod deadlocks in Init**, the istio-proxy startup probe never
  passes; discovered on first apply), and port 443 to the world (S3 +
  XSUAA + Cloud Logging). Everything else denied.

**Why now and not in the baseline.** A NetworkPolicy without a workload
is untestable and would have blocked the first request with no way to
tell a policy bug from a wiring bug. With the Deployment in the same
change, the policy is validated by the API actually serving a request.

## KA8 — One replica, explicit resource requests/limits

**Decision.** `replicas: 1`, requests `100m` CPU / `128Mi`, limits
`500m` / `512Mi`. Fits the baseline's ResourceQuota (CPU limit 4, memory
limit 8Gi) with wide headroom for the cron pods to come.

No HPA, no PodDisruptionBudget in dev. Both are promotion concerns.

## KA9 — New capability spec `btp-serving`

**Decision.** This change adds `openspec/specs/btp-serving/spec.md`, the
first capability that serves traffic from BTP. The baseline deliberately
added no spec (K10) because it served nothing. The spec records the
public-read / authenticated-write contract and the bucket-backed
persistence as behaviour, independent of the manifests that implement it.

## Open questions

- **Per-bucket S3 credentials (KA4).** Does the api-results binding's
  key actually read the cron-results bucket? Verify after apply; if it
  403s, the cron fallback is simply dark in dev until a production
  change gives the pod two credential sets. Does not block the primary
  read/write path.
- **Image pull secret.** Is `ghcr.io/clafter/scorecard-api` public? If
  the fork's packages are private, add an image pull secret. Checked
  during apply.
- **Istio sidecar and the API's readiness.** The API serves on `:8080`;
  confirm the Istio sidecar's readiness gate does not deadlock a
  single-replica rollout (known Kyma gotcha with `holdApplicationUntilProxyStarts`).
